# monkey_compiler

Thorsten Ballの『Writing A Compiler In Go』に沿って、Monkey言語のバイトコードコンパイラとスタック型の仮想マシン（VM）をGoで実装したもの。前作『Go言語でつくるインタプリタ』で作る字句解析器・構文解析器・評価器を土台にし、最終章（第10章のベンチマーク）まで進めた。

同じ本の1回目の取り組みは [compiler_go](https://github.com/peta-skr/compiler_go) で、第7章（関数）の途中で止まっている。このリポジトリは前作の完成コードから始め直したもので、ビルドとテストが通る状態で最後まで書き終えている。

## できること

- REPLで1行ずつ、字句解析、構文解析、コンパイル、VMでの実行を行い、結果を表示する。グローバル変数と定数表は行をまたいで引き継ぐ
- 値は整数・真偽値・文字列・配列・ハッシュ・関数・クロージャ
- 前置演算子 `!` `-`、中置演算子 `+` `-` `*` `/` `==` `!=` `<` `>`（文字列どうしの `+` は連結）
- `let` による束縛、`if` / `else`、`return`、配列とハッシュのリテラル、添字アクセス `a[0]` / `h["key"]`
- 関数の定義と呼び出し、ローカル変数、外側の変数を捕まえるクロージャ、再帰関数
- 組み込み関数 `len` `puts` `first` `last` `rest` `push`
- オペコードは30種類（`code/code.go`）
- ベンチマーク用のプログラムで、`fibonacci(35)` をVMと前作の評価器のどちらでも実行できる

REPLでの例。

```
>> let newAdder = fn(a) { fn(b) { a + b } }; let addTwo = newAdder(2); addTwo(3)
5
>> let fib = fn(n) { if (n < 2) { n } else { fib(n - 1) + fib(n - 2) } }; fib(15)
610
>> let m = {"one": 1, true: 2}; m["one"] + m[true]
3
>> len("hello") + len(rest([1, 2, 3]))
7
```

## 動かし方

Goが必要（`go.mod` の指定は `go 1.14`）。外部パッケージには依存していない。

```sh
go run .                          # REPLを起動
go test ./...                     # 全パッケージのテスト
go run ./benchmark -engine=vm     # fibonacci(35) をVMで実行して時間を表示
go run ./benchmark -engine=eval   # 同じプログラムを木を辿る評価器で実行
```

手元の環境で1回ずつ測ったところ、`-engine=vm` が約3.4秒、`-engine=eval` が約15.0秒だった。

## 構成

| パス | 役割 |
| --- | --- |
| `token/` `lexer/` | トークンの定義と字句解析 |
| `ast/` `parser/` | 抽象構文木と、Prattパーサによる構文解析 |
| `evaluator/` | 前作の、木を辿って評価するインタプリタ（ベンチマークの比較対象） |
| `object/` | 実行時の値と組み込み関数。評価器とVMで共有する |
| `code/` | オペコードの定義、命令のエンコード・デコード、逆アセンブル表示 |
| `compiler/` | ASTからバイトコードへのコンパイル。`symbol_table.go` で名前のスコープを解決する |
| `vm/` | スタック型VM。`frame.go` が関数呼び出しのフレーム |
| `repl/` `main.go` | REPL |
| `benchmark/` | VMと評価器の実行時間の比較 |

## 設計・実装のポイント

設計は本に沿っており、独自の言語機能は足していない。コードから読み取れる仕組みは次のとおり。

- 命令は1バイトのオペコードと、ビッグエンディアンのオペランド（2バイトまたは1バイト）で表す。定数やジャンプ先は2バイト、ローカル変数や引数の個数は1バイト
- `<` には専用の命令が無い。左右のオペランドを入れ替えて `OpGreaterThan` にコンパイルする
- `if` は、飛び先が決まる前に `OpJumpNotTruthy` / `OpJump` を仮のオペランドで出力しておき、分岐の本体をコンパイルした後で飛び先を書き換える
- シンボルテーブルを関数ごとに入れ子にし、`GLOBAL` `LOCAL` `BUILTIN` `FREE` `FUNCTION` の5種類のスコープで名前を解決する。外側の関数のローカル変数を参照すると `FREE` として登録し、`OpClosure` が関数と一緒に自由変数をクロージャへ詰める
- 再帰関数は、`let` で関数リテラルを束縛するときにパーサが関数名を記録し、関数の中から自分の名前を参照すると `OpCurrentClosure` で今のクロージャを取り出す
- 関数呼び出しはフレーム（クロージャ、命令ポインタ、ベースポインタ）を積んで行う。ローカル変数はスタック上のベースポインタから数えた位置に置く
- 組み込み関数の定義は途中で `evaluator` から `object` へ移し、評価器とVMで同じ定義を使う

## 学んだこと

- ASTを木のまま評価する方式と、バイトコードにコンパイルしてVMで実行する方式の違い。同じ `fibonacci(35)` で実行時間に4倍ほどの差が出た
- 飛び先を後から書き換えて、条件分岐をジャンプ命令に変換する方法
- 入れ子のシンボルテーブルによるスコープ解決と、自由変数を捕まえるクロージャの作り方
- 呼び出しフレームとベースポインタを使って、関数呼び出しとローカル変数をスタック上で扱う方法
